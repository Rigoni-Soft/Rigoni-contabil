# Responsável por Cliente é gravado fora do agregado Cliente

`arquitetura.md` (seção 3.6) diz que escritas passam sempre pelo agregado. O ticket #65 (Responsável por Cliente) grava `responsavel_id` em `cliente_cadastro_operacional_sn` por um repositório próprio (`ResponsavelClienteRepository`), sem reconstruir o agregado `Cliente`.

**Decisão:** manter a exceção. O Responsável é uma coluna isolada, escrita por um ator diferente do resto do cadastro (só o Líder do Simples Nacional; o Funcionário edita as demais colunas da mesma linha). Reconstruir o agregado para mudar uma coluna exigiria carregar e regravar campos que o Líder nem enxerga como dele, abrindo corrida com a edição do Funcionário. A regra fica em duas camadas: caso de uso (`AtribuirResponsavelCliente`) e banco (RLS + trigger `proteger_responsavel_cliente`, que também valida que o Responsável é Funcionário do Simples Nacional, mesmo para `service_role`).

**Auditoria no banco (devolutiva técnica da PR #71, ponto 1):** o risco que esta ADR aceitava antes — escrita direta do Líder pela Data API mudando o Responsável sem evento — foi fechado. O sucesso é auditado pelo trigger `auditar_responsavel_cliente`, na mesma transação da escrita (ator e setor da sessão do banco; se o evento não for gravado, a alteração é desfeita), como manda a regra de `arquitetura.md` §3.14. A ação sai da comparação OLD/NEW: `cliente.atribuir-responsavel`, `cliente.trocar-responsavel` e `cliente.remover-responsavel`. O caso de uso só audita a falha, em best-effort.

**"Removido/desativado" (devolutiva técnica da PR #71, ponto 2):** o sistema ainda não tem estado de usuário desativado; ele nasce no #58 (soft delete). Nesta rodada, "removido/desativado" do #65 significa **conta excluída**: o FK `responsavel_id → perfis(id) ON DELETE SET NULL` deixa o Cliente "Sem responsável", e há teste de integração para isso. Quando o #58 introduzir a desativação, ele precisa limpar `responsavel_id` do usuário desativado (critério adicionado ao #58).
